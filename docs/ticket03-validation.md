# 03: 直下の名前探索の検証

状態: 2026-10-10、直下scanの実装・該当統合試験が合格。既存のF01–F12、17ケースの独立probe監査、checkの全回帰も合格。

合成データのみを使用し、Linux/amd64・ext4上のDocker管理ボリュームをro,nodev,nosuid,noexecで提供した。製品プロセスは非root・capabilitiesなし、実行時ネットワークなし。Goと依存版・イメージは[試験Dockerfile](../tests/safefs/Dockerfile)とgo.mod/go.sumに固定する。Windowsは試験起動側で、探索の対応OSではない。

| 範囲 | 実施内容 |
|---|---|
| E10 | check成功後に同じ合成マウントをrwへ変更し、scan独自の再検査による起動拒否を確認 |
| F01–F05 | 外部/相対/祖先リンク、FIFO/socket/char/block、別FS/同一FS bind、内外ハードリンクを直下scanへ統合。syscall監査で本文open/read/mmap、子ディレクトリ列挙を拒否 |
| R03/R04 | 20,001項目で列挙20,000停止。2,001候補で保持2,000、2,001権限エラーの注入で保持200。集計と切り詰めを分離 |
| O01/O02/O06 | ESC・改行・不正UTF-8・双方向制御文字、合成AGENTS/設定/実行指示。引用とBase64、有効なJSON、本文非参照、外部通信/追加execなし |
| O03/O04 | 2,000個の長い不正UTF-8名でJSON候補領域6MiBを超過させ、残り2MiBの予約領域内にサマリー・終端を保持。候補0の上限/権限エラーもpartial |
| 障害・中断 | getdents64 EIOで6、子pin ENOENTで5、SIGTERMで143、31秒の遅延注入でdeadline/2、出力切断で7。候補取得後のopenat2 ENOSYS＋SIGTERMは内部異常4を優先して候補を保持 |

[再現手順](usage.md)から実行する。`-ScanOnly`は直下scan統合試験だけを実行する。syscall監査は失敗した禁止openも検出する負の対照を含む。障害注入は外部straceで行い、製品に保護を解除するフラグはない。

候補保持数が先に制限するため、生パス2MiB/エラー256KiBの上限到達はこの直下・255バイト名の合成ext4環境では起こらない。チェックを実装し、現在の上限から到達不能であることを確認した。キューは1バッチ256件のみ、FDは直列の固定構造で所有最大6。RSSは参考実測であり厳密なプロセスメモリ上限を保証しない。

本文・再帰・ハッシュ・重複集約、XFS実機、arm64実機、下限カーネル、破損FS、稼働中の攻撃者による変更への完全耐性はこの結果に含めない。check通過と候補0件は安全の証明ではない。

最終全回帰のR03参考RSSは38,552KiB（単一実行、20,000件）だった。go vetとLinux arm64/Windows amd64へのクロスビルドも成功した。これはarm64実機での動作検証ではない。
