# 対応環境と制限

初期版 v0.1 の対応範囲は、検証済みの環境に限定する。設計上の予定を対応済みとして掲げない。

## 検証済みと対象外の区別

| 環境 | 状態 |
|---|---|
| Linux amd64、WSL2系6.18カーネル、Docker管理ボリューム上のext4 | 初期対応。合成データでE01–E10、F01–F12、R01–R08、O01–O06とパス・mountinfo・表示のfuzzを実行済み |
| Linux arm64 | 初期対応外。クロスビルドはコンパイル確認だけ。実行時は`unsupported_environment`で拒否する |
| XFS およびその他のFS | 初期対応外。条件を満たしていても`unsupported_mount`で拒否する |
| Linux 5.10系を含む未検証カーネル系統 | 初期対応外。版番号だけでは可否を決めず、必須APIが使えなければ拒否する |
| Windows / macOSでのバイナリ直接実行 | 対象外 |

環境固有の識別子と詳細なビルド文字列はこの公開要約に含めない。同じ系統の環境すべての動作を保証する表ではない。[読み取り試作](ticket01-validation.md)、[checkの検証結果](ticket02-validation.md)、[12の結果](ticket12-validation.md)に方法と範囲を記載する。2026-10-11、未検証の arm64 実機・XFS・5.10系を初期対応から外した。公開前条件は、この縮小後の範囲で判断する。[ローカル配布候補](release-candidate.md)を参照。

## 設計上の利用条件

- 更新された信頼できるLinux調査環境と、担当者が準備した静的・読み取り専用のローカルコピー。
- 明示する絶対ルート、ext4、ro/nodev/nosuid/noexecのマウント条件。
- 非rootで、実・実効・保存UID/GIDがそれぞれ一致し、有効・許可・継承・ambient capabilitiesがないこと。
- 必須のopenat2制約とstatx情報、信頼できるホストprocfsが利用できること。
- 実行アーキテクチャはLinux amd64。

稼働中の本番サーバー、侵害OSを起動したコピー、ネットワークFS、FUSE、未検証FS、ESXi上の直接実行は初期対応外。hwhはコピー取得・マウント・展開・復旧・権限変更を行わない。試作のDocker環境は合成データ専用で、侵害コピーを扱うための隔離環境として提供していない。

## 機能と保証の限界

- 現在は単一ファイルの読取試作、check、quick優先探索と明示指定deep探索のscanを実装。終了コード・JSONと途中終了時の結果保持は[共通契約](cli-contract.md)を参照。名前候補の本文取得・完全ハッシュ、内容ルール、完全ハッシュによる[上限付き集約](deduplication.md)、通常表示は既定でジョーク付き。JSON・quietと`--no-joke`では抑制され、探索結果や終了状態を変更しない。初期資源値と20例の内容ルールは[11の合成評価](ticket11-validation.md)を通過したが、実環境の性能・精度保証ではない。
- リンク、別マウント、特殊ファイル、nlinkが1以外の通常ファイルを本文読み取りから除外する。この制限で見落とす場合がある。
- 本文取得対象は1MiB未満。1MiB以上は本文open前に除外。総読取量は64MiB以内で、EOF確認の余裕がない場合も開始しない。[本文契約](body-read-contract.md)を参照。
- 読み切りと前後の属性確認は、動的な対象の完全な一貫性や、保持した実体の現在位置を証明しない。
- 同期I/Oをcontextで強制中断できるとは保証しない。読み取りによるアクセス時刻への影響も、完全にないとは保証しない。
- 調査OS、カーネル、FSドライバ、仮想化基盤の安全性は前提。プロセス全体のサンドボックス化や、悪意あるディスクイメージの安全なマウントを提供するものではない。
- 候補なしは侵害なしの証明ではない。検出の完全性、復旧、証拠保全を保証しない。

quickの再帰・公平性・予算と合成データの初期資源観測は[05の検証結果](ticket05-validation.md)を参照。実機で検証した環境はLinux amd64/ext4だけ。

内容ルールと一般名の本文取得の結果は[06の検証結果](ticket06-validation.md)を参照。

deepの深さ・キュー・パス・境界保護と初期資源観測は[07の検証結果](ticket07-validation.md)を参照。11では200,000項目と512MiB本文境界を合成負荷で実測した。300秒経過による公開CLIの期限到達は未実施。

同一完全ハッシュの集約、2,001コピーのパス切り詰め、異内容・ハッシュなしの分離は[08の検証結果](ticket08-validation.md)を参照。11では200,000候補・198,001グループを合成評価した。

候補保持後の予算・対象変化・I/O障害・シグナル・必須機能喪失、通常/quiet/JSON、出力切断の組み合わせは[09の検証結果](ticket09-validation.md)を参照。停止したカーネルI/Oの硬い中断期限は保証しない。

20万候補、512MiB本文境界、待ち行列、深さ、大量エラーの測定では既存上限を維持したため、初期予算を変更していない。測定条件と値は[評価方法](evaluation-method.md)と[結果](ticket11-validation.md)を参照。この性能は検証済みのLinux amd64/ext4合成環境に限る。

実データを持ち込む前の[無害な合成デモ](safe-demo.md)では、同じLinux amd64/ext4環境で`check`、書き込み可能経路の拒否、quick、deep、JSON、除外と不完全状態を確認できる。デモ用の特権準備コンテナは合成データ専用であり、侵害コピーの隔離・mount環境ではない。[検証結果](ticket13-validation.md)も参照。
