# 09 途中終了と結果状態の検証

検証日: 2026-10-11

## 結果

Linux amd64の合成ext4コピーで、完了、候補あり、不完全、起動拒否、対象・環境変化、I/O障害、必須保護機能喪失、SIGINT/SIGTERM、協調期限、出力切断の終了状態を公開CLIから確認した。quickで候補を保持した後に対象消失、I/O障害、SIGTERM、必須機能喪失を注入しても、検証済みの候補を予算内で残し、新しい読み取りを停止した。deepでも同一ハッシュの候補を集約した後のSIGINTで、保持済みグループと不完全状態を返した。

対象の消失・版または同一性の不一致は`target_changed`、マウント等の条件変化は`environment_changed`、探索開始後の必須機能喪失は`security_invariant_failed`として区別する。終了コードの優先順位は、同時に注入した必須機能喪失がシグナルより優先することを確認した。permission_denied、file_size_limit、方針除外、予算、I/O障害も別の詳細・集計に残る。

通常表示は完了結果をstdout、不完全・停止をstderrへ出し、quietでも不完全理由と集計を残した。JSONはstdoutの一オブジェクトで、通常の8MiB出力上限では終端・サマリーを保持した。stdoutまたはstderrの受信側を閉じた場合はSIGPIPEで終了せず終了コード7を返した。この場合、物理的に切れたJSONや端末出力の完結は保証しない。

全回帰の参考観測ではscanの最大RSSは約89MiB、独立traceでの探索用peak FDは12だった。これらは合成fixtureに対する一回の観測であり、厳密な上限や他環境の性能値ではない。

## 実施条件

- Go 1.27.2、golang.org/x/sys v0.49.0、CGO無効
- Linux amd64、WSL2系の保守中カーネル
- Docker管理ボリューム上のext4をro,nodev,nosuid,noexecでbind mount
- hwhと監査処理はUID/GID 1000、capabilitiesなし、ネットワークなし
- 合成テキスト、合成リンク、FIFO、デバイスノード、bind mount、tmpfsだけを使用

## 対応した試験

- F09/R07: シグナル、期限、エラー、panic相当の故障経路で所有FDを回収し、観測上限32を守る。
- R02/R04: 本文・列挙・起点・キュー・候補・エラー・出力の上限到達を不完全状態として残す。
- R05: 本文や列挙済み対象の変化を候補なしや単件スキップへ変換せず全体停止する。
- O01/O02/O03: 敵対的な名前をエスケープし、JSONシリアライザと予約領域で有効な上限内出力を作る。
- O04: 候補数、保持結果、方針除外、項目エラー、予算、停止理由を分離する。
- 回帰: E01–E10、F01–F12、実装済みのR01–R08とO01/O02/O04/O06、quick/deep、本文、内容ルール、集約。

## 未検証・保証しない範囲

Linux arm64実機、XFS、Linux 5.10系の実行は未検証で、クロスビルド成功を代用しない。SIGKILL、ランタイムの回復不能障害、停止したカーネルI/Oに対する結果出力や硬い終了期限は保証しない。厳密なRSS上限、最大20万項目・512MiB・300秒への実負荷到達は11以降の範囲である。

保持済み結果は停止までに観測・検証できた範囲だけを示す。中断後の未探索範囲、コピー全体の一貫性、候補がないこと、侵害の有無を証明しない。
