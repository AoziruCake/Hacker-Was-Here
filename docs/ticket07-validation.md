# deep探索の検証結果

検証日: 2026-10-10。Linux amd64、WSL2系6.18カーネル、Docker管理ボリュームのext4、ro/nodev/nosuid/noexec、UID/GID1000・capabilitiesなし。Go1.27.2 / x/sys v0.49.0 / CGO無効。合成データのみ、試験時ネットワークnone。再現は[既存のDocker手順](usage.md)。

## 実装と確認

- `scan --deep`を明示した場合だけ、root一起点のFIFO探索を深さ64、列挙200,000、本文512MiB、協調期限300秒へ切り替える。無指定と`--quick`は従来動作で、同時指定・重複・`check --deep`は拒否する。
- quickとdeepを同じ合成コピーへ実行し、深さ6の候補がdeepだけで追加されることを公開CLIで確認。深さ64の通常ファイルを検査し、深さ64のディレクトリを`depth_limit`として列挙しないことも確認した。
- deepでも固定root FD、openat2の4制約、O_PATH pin、proc経由の再取得、属性・マウント再照合、本文・内容ルール、表示を共有する。範囲外リンク、別マウント2種、FIFOを本文用open/readせず除外し、独立strace監査で範囲外canaryの取得・readがないことを確認した。
- 4,100個の待ちディレクトリで`queued_paths`、dirfdで作った4,096バイト以上の相対パスで`path_bytes`となり、有効な部分結果を返すことを確認。観測ピークFDは8で、上限32以内だった。
- SIGTERMの協調中断を公開CLIで確認。300秒設定と期限切れcontext、512MiB境界直前から追加本文を開始しない動作は単体試験で確認した。
- 既存F01–F12と17probe、check、scan/E10、本文、quick、内容ルールを含むLinux全回帰が合格。最終のscan統合試験も別実行で合格した。
- `go vet ./...`、Linux arm64・Windows amd64クロスビルド成功。実機試験とは区別する。

## 初期資源観測

4,100個の空ディレクトリを持つ合成コピーの非trace deep実行は約0.059秒、最大RSS 12,668KiB、列挙4,100、独立traceでのピークFD 8だった。単一環境・小さい合成入力の参考値であり、200,000項目や512MiBを実際に処理した性能値、厳密なメモリ上限、実データの所要時間ではない。

## 残る制限

11で列挙200,000到達と本文512MiB境界を公開CLIの合成負荷で実測し、初期基準を満たした。[資源評価結果](ticket11-validation.md)を参照。300秒経過による公開CLIの期限到達は未実施。境界値・期限設定・協調停止は小さい合成試験と単体試験で確認済みで、対応環境横断は12で行う。

XFS、arm64実機、下限カーネルは未検証。同期I/Oを300秒で強制中断する保証、動的コピーの完全な時点一貫性、候補なしによる侵害なしの証明は提供しない。ハッシュ集約は未実装。
