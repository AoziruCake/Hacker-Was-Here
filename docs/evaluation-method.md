# 資源予算と検出品質の評価方法

11の測定前に確定したQ15の方法と合否基準。安全性試験、実環境での検出率、厳密な資源保証とは分けて扱う。

## 条件と指標

既存のLinux amd64、WSL2系6.18カーネル、Docker管理ボリューム上のext4を使う。対象はro/nodev/nosuid/noexec、hwhはUID/GID 1000・capabilitiesなし・無通信で実行する。コンテナは2 CPU、512MiBに制限し、CPU情報は非公開の実行artifactへ記録する。物理CPUや他の負荷が異なる環境へ時間を一般化しない。

公開CLIのquick/deepをJSONで実行し、経過時間、最初のstdout、Linuxが記録する最大RSS、JSONの本文読取量・列挙数・保持件数・出力量を測る。最初の候補時間は、現在のCLIが完成レポートを一括出力するため「候補を含むstdoutの出力開始まで」と定義する。内部で候補を検出した瞬間や対話的な逐次表示の時間ではない。

FDはprocfsから他プロセスのFD一覧を取得できない条件があるため、同じ非特権CLIをstraceで別実行し、成功したopenとcloseからquick/deepの観測ピークを数える。traceの時間は性能値に使わず、生traceを公開・コミットしない。I/Oは製品が集計する対象本文の実readバイトを正とし、子プロセスのblock input/output操作数も補助記録する。後者が0でもページキャッシュ等があるため「I/Oなし」と解釈せず、物理ディスクバイトの保証には使わない。

## 合成負荷

- quick: 5起点に計20,001項目。全体列挙上限と起点巡回を確認する。
- deep集約: 200,000個の名前候補。2,000個は同一本文、残りは異なる小本文とし、列挙・集約キー・候補保持を同時に確認する。
- deep本文: 1MiB未満のsparse通常ファイル513個。512MiB総読取境界を実readで到達させる。
- 待ち行列と深さ: 4,100空ディレクトリ、別に深さ64の候補を用意する。
- エラー: 読取権限のない名前候補1,000個を用意する。
- 検出品質: ルール実装前に期待値を決めた20例を変更せず使う。意味上の陽性13例、陰性7例で、英語の一致・別表現・日本語・HTML分断・教育引用・UTF-16・不正UTF-8・NUL/ESCを含む。

すべて無害な合成データであり、実際の要求文、被害データ、秘密情報は使わない。

## 測定前の合格基準

- quickは30秒以内かつ最大RSS 256MiB以下、deepは300秒以内かつ最大RSS 384MiB以下。
- 候補を含むstdoutの出力開始も各モードの期限内。
- traceで観測するFDは40以下。製品設計上の探索所有上限32とは測定方法が異なり、標準FD等も含む保守的な外側基準とする。
- 本文read、列挙、候補パス2,000件、エラー200件、出力8MiBの既存上限を超えず、到達時は対応する`limits`と不完全状態を返す。
- 20例の期待ルールが全件一致し、どちらかの内容ルールについてprecision 80%以上、recall 40%以上。UTF-16、不正UTF-8、NUL/ESC入りは内容候補にしない。

precision/recallの低い基準は、意図的に既知の見落としと教育引用の誤検出を含めた小集合に対する初期版の受入値である。公開後の実環境精度や安全性の基準ではない。結果を見てこの基準を変更せず、未達なら原因と変更影響を記録する。保護解除、無制限設定、製品用の測定オプションは追加しない。
