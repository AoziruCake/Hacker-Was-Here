# checkの検証結果

検証日: 2026-10-10。対象は起動条件を確認する公開CLI `hwh check`。[共通契約](cli-contract.md)のうちcheckを実装し、scanは予約契約のみ。実際の侵害コピーを扱う公開リリースの判定ではない。

## 環境と方法

Linux amd64、WSL2系6.18カーネル、Docker管理ボリュームのext4、Go 1.27.2、x/sys v0.49.0、CGO無効。Dockerfileのベースイメージはdigest固定。arm64とWindowsのCLIはクロスビルド成功、`go vet ./...`も成功。実機での成立を意味するのはamd64/ext4だけ。

合成データを新規ボリューム内に準備し、ネットワーク・ホストディレクトリ・Dockerソケットを渡さないコンテナで実行した。マウント準備はハーネスのみ。検査は非root・capabilitiesなしで行い、権限拒否の試験だけ起動資格情報を変えている。

`tests/check/check_cli.py`は製品バイナリを起動し、端末・JSON・終了コードを照合する。straceで列挙、本文用open、read系、mmap、マウント・権限変更を監視する。分割されたsyscall行も結合して監査する。監査器には禁止操作を含む負例を与え、検出できることを確認した。実行環境のprocfsやGoランタイムが読むホスト情報は、対象本文とは区別する。

必須syscallの故障・欠落属性・壊れたmountinfoはstraceの外部故障注入で再現した。製品CLIや環境変数に検査回避機能は追加していない。注入順序は実測traceから取り、注入が起きたことも確認する。mountinfoの一部破損試験ではフィクスチャが返るチャンク位置も検査し、異なる環境で条件が成立しなければ試験を失敗させる。

checkの監視対象ケースでは配下列挙・対象本文のread/mmap・本文用open・マウント/権限変更は0件。E03の資格情報切替と偽procの準備処理は別ハーネスで行い、製品の操作として数えていない。メタデータの過大試験では4096バイトのreadを256回で停止することも確認した。再取得時のFS条件も再確認する。故障注入と負例を含む全回帰が合格した。

## 未実施・限界

arm64実機、XFS、API下限カーネル、NFS/SMB/FUSE/btrfs等の個別実マウント試験は未実施。列挙・本文解析・検出・scanのレポート、E10、R/Oの残りは後続チケットの範囲。checkの合格はコピーの真正性・静的状態・侵害の有無を証明しない。シグナル処理は協調的で、停止したカーネルI/Oを強制的に終了させる保証はない。

この試験はcheckと既存読み取り境界の回帰を対象とする。全FS/全カーネル、全競合やランタイム障害への保証ではない。生ログ、実行ID、個人パス、詳細な環境識別情報は公開しない。
