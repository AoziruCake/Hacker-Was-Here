# ローカル配布候補

この文書は、初期版を配布できるかを判断するためのローカル公開準備である。外部サービスへの投稿、GitHub Releasesへのアップロード、リポジトリの公開設定変更は含まない。

2026-10-11、初期対応をLinux amd64／検証済みカーネル系統／ext4へ縮小した。この範囲では、固定依存の単一バイナリを起動し代表操作できる。縮小前に公開を止めていた V02（arm64実機・XFS・5.10系）は、対象外へ移したため公開不可残件ではない。push、Releases、公開設定変更は別操作であり、この文書では実施しない。

## 配布物

ローカル生成物はGit管理外の`dist/`相当へ置く。公開リポジトリにはバイナリを含めない。

| ファイル | 内容 |
|---|---|
| `hwh-linux-amd64` | CGO無効、`-trimpath`のLinux amd64実行体 |
| `SHA256SUMS` | 上記ファイルのSHA-256。破損検知用 |
| `LICENSE` | 著作権留保。利用許諾なし |
| `build-info.txt` | 製品版、Go、x/sys、ソースcommit、成果物ハッシュ |

arm64クロスビルドはコンパイル確認だけに使い、配布物へ含めない。実行時は拒否する。CLI版表示は`0.1.0-dev`のままである。公開可能なv0.1.0タグは、所有者が外部公開を行うときに付ける。

Linux上で、ビルド済みの静的amd64バイナリからローカルの`.deb`を作る準備だけがある。aptリポジトリ、PPA、公開アップロードは作らない。パッケージメタデータは利用許諾を与えない。`dpkg -i`の実機確認は未実施である。

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o dist/hwh-linux-amd64 ./cmd/hwh
scripts/build-deb.sh
```

`scripts/build-deb.sh`は`dpkg-deb`が必要である。成果物は`dist/hwh_0.1.0-dev_amd64.deb`で、Git管理外である。

## 生成と確認

固定した試験イメージから、成果物の再ビルドとハッシュしたamd64実行体の代表操作を行う。

```powershell
docker build --progress plain -t hwh-safefs-lab:ticket14 -f tests/safefs/Dockerfile .
./tests/release/run.ps1 -Image hwh-safefs-lab:ticket14
```

ビルド時とgovulncheckだけが通信する。成果物の起動と`check`／quick／deepは`--network none`で実行する。手順は[無害な合成デモ](safe-demo.md)と同じ合成コピーを使い、`/opt/hwh`ではなく再ビルドしたamd64成果物を実行する。

## Q12. ライセンス・真正性・リリース手順

著作権は留保し、利用許諾は与えない。一次資料はリポジトリの[LICENSE](../LICENSE)である。オープンソースライセンス（OSIやSPDXの`MIT`など）は採用しない。

チェックサムと真正性は分ける。

- SHA-256は、手元のファイルが`SHA256SUMS`と同じかを見る破損検知である。
- 真正性は、実行体と`SHA256SUMS`を同じ公式配布元から得たことの確認である。信頼できない場所にあるチェックサムは出所を証明しない。
- 初期の公式配布元は、このプロジェクトの公式GitHubリポジトリとする。リポジトリがprivateの間は、所有者が渡したローカル成果物だけを配布元とみなす。

公開できるようになったあとのGitHub Releases手順（未実施）:

1. この文書の公開不可残件が空であることを確認する。
2. 固定toolchainで本ハーネスを再実行し、成果物ハッシュと検証記録を対応付ける。
3. 注釈付きタグ（例: `v0.1.0`）をソースへ付ける。
4. 公式リポジトリのReleasesへ、Linux amd64実行体、`SHA256SUMS`、`LICENSE`、`build-info.txt`を同じリリースへ添付する。
5. 利用者が公式Releasesから実行体と`SHA256SUMS`を取得し、ハッシュを照合する。
6. 非公式ミラーや、チェックサムだけ別サイトにある配布物は使わない。

アカウント侵害や改ざん済みリリースまで防ぐ署名付きタグは、所有者が用意した場合の追加手段であり、初期必須にはしない。このチケットでは上記手順を実行しない。

## Q13. 報告と更新

通常不具合は公式リポジトリのGitHub Issuesへ報告する。脆弱性や安全要件を破る重大問題は公開Issueにせず、[問題報告](../SECURITY.md)のとおりGitHub Security Advisories、またはprivate中の所有者への非公開連絡を使う。

告知・修正・更新の判断はリポジトリ所有者が行う。期限や継続保守の約束はない。自動更新はない。新しい版は同じ公式配布元から取得し、そのリリースのSHA-256と照合する。

## 添える検証と限界

| 資料 | この候補への意味 |
|---|---|
| [11の評価](ticket11-validation.md) | Linux amd64/ext4の初期予算と20例検出品質。実環境精度ではない |
| [12の結果](ticket12-validation.md) | 縮小後の対応範囲での36ケースとfuzz |
| [13のデモ](ticket13-validation.md) | 合成コピーでの利用手順。実データの隔離手順ではない |
| [対応環境](supported-environments.md) | 検証済み範囲、対象外、見落とし、保証しないこと |

実行時の追加依存は、直接依存が`golang.org/x/sys`だけであることと、成果物に動的リンカ（`PT_INTERP`）がないことで確認する。外部通信は、製品コードがHTTP/TLSを依存に含まないことと、成果物が無通信コンテナで起動・探索できることで確認する。通信しないことの完全証明や、未知脆弱性がないことの保証ではない。
